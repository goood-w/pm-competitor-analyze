## 简介

### 这个 Skill 是什么？

`pm-competitor-analyze` 是一个帮助产品经理快速产出竞品分析文档的 Codex Skill。

它的重点不是生成“大而全”的行业报告，而是围绕一个明确的产品问题，把 PRD、用户手册、更新日志、页面截图、官方说明和公开材料转化为可追溯的产品判断。

适合回答的问题包括：

- 这个功能要不要做？
- 竞品这个页面为什么这样设计？
- 我方 PRD 和竞品用户手册相比缺了什么？
- 某个标杆产品的机制能不能借鉴？
- 一个新市场或新赛道是否值得进入？

### 设计目标

- 让竞品分析从“资料堆砌”变成“支持产品决策”。
- 优先处理用户手头已有的高质量材料。
- 输出能直接复制到飞书、Notion、PRD 附录或汇报文档。
- 明确区分事实、官方说法、用户评价、分析推断和待验证假设。

## 核心特点

| 特点 | 说明 |
|---|---|
| 专项优先 | 默认聚焦一个模块、页面、流程或决策问题，不强行做全景报告 |
| 证据可追溯 | 要求记录来源、日期、版本、地区、账号和体验条件 |
| 四种模式 | 支持专项能力对比、单品机制拆解、页面/流程拆解、市场/战略扫描 |
| 固定输出 | 提供可复制的 Markdown 报告结构和表格模板 |
| 决策导向 | 使用 `adopt / adapt / avoid / test` 收敛建议 |
| 不盲目模仿 | 明确竞品做法的适用前提、迁移成本和验证方式 |

## 适用场景

### 适合使用

- 产品经理要为 PRD、版本规划或功能取舍补充外部证据。
- 已经有我方方案，需要对比竞品用户手册、帮助中心或更新日志。
- 想拆解竞品官网、注册流、购买页、AI 生成页或其他关键页面。
- 想学习某个标杆产品的单个机制，例如评分、推荐、配置、付费、反馈闭环。
- 要做轻量的市场进入、商业模式或战略扫描。

### 不适合使用

- 只想无目标罗列所有竞品功能。
- 只凭几张截图就断言完整产品规则或业务效果。
- 想把“竞品有”直接转成“我们也要做”。
- 需要法律、财务、医疗等高风险结论但没有可靠来源。

### 场景示例

```text
场景1：PRD 证据补充
我方正在设计“简历优化前评分”功能，需要分析竞品是否先展示评分、差距和付费入口。

场景2：页面转化拆解
想看一个 AI 产品的落地页如何建立信任、降低试用门槛、推动注册。

场景3：单品机制学习
想拆解某个招聘产品如何组织 JD、简历、面试题和反馈闭环。

场景4：市场/战略扫描
准备进入一个新赛道，需要先看竞品定位、用户、商业模式和机会风险。
```

## 快速开始

### 本地安装

把本目录复制到 Codex Skills 目录：

```bash
mkdir -p ~/.codex/skills
cp -R pm-competitor-analyze ~/.codex/skills/
```

如果使用发布包：

```bash
mkdir -p ~/.codex/skills
ditto -x -k dist/pm-competitor-analyze.skill ~/.codex/skills
```

### 最快上手

在 Codex 新对话中直接点名：

```text
请用 $pm-competitor-analyze，基于我的 PRD 和这几个竞品用户手册，分析“简历优化前是否需要先展示评分与差距”。
```

更稳定的输入格式：

```text
请用 $pm-competitor-analyze 做竞品分析。

我方产品：
目标用户：
本次决策问题：
我方当前方案 / PRD：
竞品对象：
已有材料：
希望输出：
```

## 使用方法

### 方法1：通过 Codex Skill 使用

```text
请用 $pm-competitor-analyze 分析以下竞品材料，并输出 Markdown 竞品分析文档。
```

Codex 会按当前任务选择合适模式，并在必要时读取 `references/` 中的材料规则和模板。

### 方法2：手动参考框架

如果你想自己手动做分析：

1. 先读 `SKILL.md`，明确模式和完成标准。
2. 按 `evidence-rules.md` 盘点材料和证据等级。
3. 从 `report-templates.md` 复制对应模板。
4. 填入事实观察、来源、差异解释和建议。
5. 用 `adopt / adapt / avoid / test` 收敛行动。

### 方法3：作为 GitHub Skill 项目同步

把整个 `pm-competitor-analyze/` 目录作为仓库根目录提交即可。建议至少保留：

- `SKILL.md`
- `README.md`
- `CHANGELOG.md`
- `agents/openai.yaml`
- `references/`
- `dist/`

## 分析模式

| 模式 | 适合场景 | 典型输出 |
|---|---|---|
| 专项能力对比 | 模块改版、PRD 决策、功能取舍 | 多对象对比表、差异解释、版本建议 |
| 单品机制拆解 | 学习一个标杆产品或机制 | 机制拆解表、可借鉴/不可借鉴项 |
| 页面/流程拆解 | 官网、注册流、购买页、AI 生成页 | 用户旅程、UI 元素意图、转化学习点 |
| 市场/战略扫描 | 市场进入、商业模式、竞争格局 | 竞争地图、机会风险、阶段建议 |

默认优先选择最轻模式。只有用户明确需要市场、战略或商业模式分析时，才展开完整扫描。

## 输入材料建议

最好提供以下材料：

| 材料 | 作用 |
|---|---|
| 我方 PRD / 当前方案 | 作为对比锚点 |
| 竞品用户手册 / 帮助中心 | 判断实际功能、规则、配置和边界 |
| 产品截图 / 录屏 / 实操记录 | 判断入口、流程、状态、异常和反馈 |
| 更新日志 / 发布记录 | 判断迭代重点和资源投入 |
| 价格页 / 套餐说明 | 判断商业边界和付费策略 |
| 官方案例 / 白皮书 / 财报 | 判断客户、战略和组织能力 |
| 第三方报告 / 新闻 / 用户评论 | 作为补充线索，不单独支撑核心结论 |

材料不足时，Skill 会保留证据缺口，而不是用行业常识补造成事实。

## 输出内容

默认输出 Markdown 文档，通常包含：

1. 决策问题与一句话结论
2. 分析范围、对象选择与材料说明
3. 统一任务脚本或机制问题清单
4. 证据台账摘要
5. 竞品对比或单品机制拆解
6. 关键洞察：共性、差异、原因
7. 对我方产品的建议：`adopt / adapt / avoid / test`
8. 对需求、版本规划或验证动作的影响
9. 证据局限与后续补证据计划

## FAQ

### Q: 应该分析几个竞品？

A: 日常产品决策建议 2-5 个。少于 2 个容易缺少对照，多于 5 个会明显增加材料成本。单品机制拆解可以只分析 1 个对象。

### Q: 没有完整竞品资料怎么办？

A: 可以先做轻量分析，但要标注证据缺口。截图只能证明页面表现，用户评论只能提供线索，不能直接证明完整规则或业务效果。

### Q: 这个 Skill 会自动联网找资料吗？

A: 它可以配合 Codex 的联网能力使用，但设计上优先消化用户提供的高质量材料。涉及价格、政策、版本、市场数据等易变信息时，应重新核对来源和日期。

### Q: 为什么不默认使用 10 大维度？

A: 因为日常产品决策更需要快、准、可行动。10 大维度适合市场/战略扫描，不适合每一次模块级竞品分析。

### Q: 输出能直接变成 PRD 吗？

A: 不能直接替代 PRD。竞品分析只说明外部做法、适用条件和证据边界；真正的需求范围还要结合我方用户、业务目标、技术约束和验证结果。

### Q: 如何持续更新竞品分析？

A: 可以按月或按版本更新：

```text
月度：
- 更新竞品发布记录和价格页
- 记录关键页面或流程变化
- 补充用户评价中的新反例

版本前：
- 对照我方 PRD 和竞品用户手册
- 检查新增能力、规则变化和商业边界
- 更新 adopt / adapt / avoid / test 建议
```

## 最后说明

竞品分析的目标不是证明“别人做了所以我们也要做”，而是回答：

> 竞品为什么这样做？它依赖什么前提？我方是否具备这些前提？如果要借鉴，应该直接采用、改造、避免，还是先测试？

这也是本 Skill 的核心设计原则。
