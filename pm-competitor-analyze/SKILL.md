# pm-competitor-analyze

帮助用户把竞品材料转化为能支持产品判断的分析文档。默认做“以我方目标为锚点的专项分析”，而不是泛泛的行业大报告。

## 优先读取

- 需要了解本 Skill 设计来源或向用户解释方法论时，读 [链接分析与 Skill 设计沉淀](./references/source-analysis-and-design.md)。
- 开始采集、整理或判断材料可信度前，读 [材料与证据规则](./references/evidence-rules.md)。
- 需要直接输出报告、表格或 Markdown 结构时，读 [竞品分析报告模板](./references/report-templates.md)。

## 先收敛问题

开始前尽量明确以下信息；缺少会改变结论的关键项时再追问：

- 本次要支持的产品决策、学习问题或待验证假设。
- 我方产品、目标用户、核心场景、当前方案或 PRD。
- 分析对象：直接竞品、间接替代、标杆页面、现有人工流程。
- 时间、地区、端、账号、版本、付费层级等体验条件。
- 交付形式：快速 Markdown、深度报告、表格底稿、PPT 摘要、页面拆解。

如果用户只说“帮我做竞品分析”，先把问题改写成可分析的问题，例如“我们是否需要在简历优化前暴露评分与差距？”或“这个页面如何促进用户完成付费转化？”

## 选择分析模式

默认选择最轻、最能回答问题的模式。

- `专项能力对比`：围绕一个模块、流程或能力，对比 2-5 个对象。适合 PRD、版本规划、功能取舍。
- `单品机制拆解`：围绕一个标杆产品或页面，解释它的用户任务、流程规则、前提和代价。适合学习某个机制。
- `页面/流程拆解`：围绕截图、落地页、购买页、注册流、配置页等，拆页面目的、用户旅程、UI 元素、心理机制和风险。
- `市场/战略扫描`：只在用户明确要判断市场进入、融资叙事、长期战略或商业模式时使用；不要默认铺开 10 大维度。

## 工作原则

- 聚焦比全面重要：一次只分析一个模块、专项能力、页面或决策问题。
- 先材料后推断：用户手册、官方帮助、产品实操、更新日志和 PRD 优先；行业报告、新闻、公众号、招聘信息只作为补充线索。
- 把证据分层：事实观察、官方说法、用户评价、数据估算、分析推断、待验证假设必须分开。
- 对比必须同口径：多对象对比使用同一用户身份、前置条件、任务脚本和观察维度。
- 结论要解释差异原因：不要停在“有/没有”“更好看”；说明差异来自目标用户、场景风险、商业模式、数据能力、运营能力、合规或历史包袱。
- 建议必须回到我方：每条建议写清解决的问题、适用前提、收益、风险和验证方式。

## 执行流程

1. 定义决策问题、分析模式、范围与非目标。
2. 盘点材料，并按可信度和用途标注：我方材料、竞品官方材料、更新日志、页面/截图、第三方资料、用户评价。
3. 设计统一任务脚本或机制问题清单。
4. 建立证据台账，记录来源、日期、版本、体验条件和可信度。
5. 按相关维度分析，不为填框架强行展开无关内容。
6. 输出关键模式、差异、原因解释和 `adopt / adapt / avoid / test` 建议。
7. 写明证据局限、待验证项和下一步补证据方式。

## 默认输出

优先输出一份可复制到飞书、Notion 或 PRD 附录的 Markdown 文档：

1. 决策问题与一句话结论
2. 分析范围、对象选择与材料说明
3. 统一任务脚本或机制问题清单
4. 证据台账摘要
5. 竞品对比或单品机制拆解
6. 关键洞察：共性、差异、原因
7. 对我方产品的建议：`adopt / adapt / avoid / test`
8. 对需求、版本规划或验证动作的影响
9. 证据局限与后续补证据计划

## 完成标准

- 报告回答了一个明确的产品问题，而不是展示资料堆砌。
- 关键判断能回溯到来源、日期、版本或体验条件。
- 输出区分事实、评价、推断和假设。
- 建议不是“竞品有所以我们也做”，而是说明适用前提和验证方式。
- 未公开、无法体验、可能过期或冲突的信息没有被补造成确定结论。
